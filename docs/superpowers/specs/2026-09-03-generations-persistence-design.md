# Generations Persistence Design

## Scope

Add full CRUD support for natal charts and neutral generations. Both resources belong to an existing person and cannot exist without one. Replace the legacy `readings` naming and `NeutralChartReading`/`NeutralGeneration` types with consistent `generations` and `GenerationNeutral` naming.

## Package Structure

```text
app/domain/generations/
  astro_charts/
    __init__.py
    models.py
    schemas.py
  generation_neutral/
    __init__.py
    models.py
    schemas.py

app/repositories/
  astro_chart_repository.py
  generation_neutral_repository.py

app/services/
  astro_chart_service.py
  generation_neutral_service.py

app/api/v1/generations.py
```

The existing `app/domain/readings` package and legacy neutral-generation repository are removed after their imports and tests move to the new names.

## Persistence Models

### `astro_charts`

- `id`: PostgreSQL UUID primary key generated by `uuidv7()`.
- `person_id`: required UUID foreign key to `persons.person_id` with `ON DELETE CASCADE`.
- `natal_xml`: required `TEXT` containing the complete XML document. The application consumes it as a whole and does not query individual XML nodes, so PostgreSQL's XML type adds no useful behavior.
- `chart_svg`: required `TEXT` containing a permanent S3 object key. Expiring presigned URLs are generated only for API responses.

### `generation_neutral`

- `id`: PostgreSQL UUID primary key generated by `uuidv7()`.
- `person_id`: required UUID foreign key to `persons.person_id` with `ON DELETE CASCADE`.
- `used_model`: required `TEXT`.
- `prompt`: required `TEXT`.
- `token_usage`: required `JSONB`.
- `result`: required `JSONB`, validated through `GenerationNeutralResult` at the application boundary.

`Person` exposes `astro_charts` and `generation_neutral` ORM collections. Each child exposes a `person` relationship. The foreign keys enforce ownership in PostgreSQL; ORM relationships provide object navigation.

## Schemas

Each resource has dedicated create, update, and read schemas. `person_id` is required when creating either resource and is not accepted by update schemas.

`GenerationNeutralResult` replaces `NeutralChartReading`. It strictly models the approved JSON document:

- `blocks` in the required order: `general`, `love`, `work_money`, `inner_demons`;
- each block contains `id`, `title`, `summary`, `facts`, and `hooks`;
- facts contain stable IDs, statement, kind, themes, importance, and typed evidence;
- hooks contain stable IDs, type, fact references, neutral angle, and priority;
- hook references must point to facts in the same block;
- fact and hook IDs must be unique in the complete result.

The old `NeutralChartReading` and `NeutralGeneration` schema names are removed rather than aliased.

## Repositories and Services

`AstroChartRepository` and `GenerationNeutralRepository` contain only SQLAlchemy persistence operations: create, list by person, get, partial update, and delete.

`AstroChartService` and `GenerationNeutralService` own application behavior:

- verify that the required person exists before create and list;
- return domain `NotFoundError` for missing persons or resources;
- commit successful mutations;
- keep `person_id` immutable;
- produce a fresh presigned chart URL from the stored S3 object key when returning an astro chart.

No generic CRUD base class is introduced because the two services already differ in S3 handling and result validation.

## HTTP API

One router is registered with:

```python
router = APIRouter(prefix="/generations", tags=["generations"])
```

Routes:

```text
POST   /api/v1/generations/astro-charts
GET    /api/v1/generations/astro-charts?person_id=<required UUID>
GET    /api/v1/generations/astro-charts/{id}
PATCH  /api/v1/generations/astro-charts/{id}
DELETE /api/v1/generations/astro-charts/{id}

POST   /api/v1/generations/neutral
GET    /api/v1/generations/neutral?person_id=<required UUID>
GET    /api/v1/generations/neutral/{id}
PATCH  /api/v1/generations/neutral/{id}
DELETE /api/v1/generations/neutral/{id}
```

Create returns `201`, delete returns `204`, missing persons/resources return `404`, and invalid request data returns `422`.

## Migration and Compatibility

Database metadata imports both new models. Because `app/db/migrations/versions` is currently empty, one initial migration creates the `users` and `persons` dependency tables followed by `astro_charts` and `generation_neutral`; its downgrade drops them in reverse dependency order. No compatibility alias remains for `app.domain.readings`, the old `neutral_generations` table name, or the old repository name; internal imports and tests move atomically.

## Verification

Implementation follows red-green-refactor. Tests cover strict neutral-result validation, required ownership and cascade metadata, both repository CRUD paths, service ownership/commit behavior, HTTP CRUD contracts, application route registration, and affected import renames. The targeted suite, compilation, diff validation, and full available test suite are run before completion.
